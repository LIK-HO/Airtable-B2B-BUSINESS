# Lead Factory Contract — B2B BUSINESS

## 1. Цель

Система лидогенерации B2B должна работать по цепочке: поиск → обогащение → автоматическая проверка → дедупликация → фильтрация → готовая выдача оператору.

Главный KPI — не число сырых найденных записей, а число готовых к работе лидов, прошедших обязательные контрольные ворота.

## 2. UX-принцип

Перед глазами оператора только один основной рабочий экран «Готовые лиды». Технические очереди, пулы, проверки, ошибки и служебные статусы скрыты.

Новые записи попадают в рабочую выдачу автоматически. Оператор не подтверждает очевидные проверки и не обслуживает конвейер данных. Он занимается только продажей и реальной обработкой результата.

## 3. Внутренняя модель

Одна каноническая сущность «Лид» с внутренним жизненным циклом. Отдельные пулы допускаются как внутренние представления одной сущности, но не создаются отдельными таблицами без доказанной необходимости.

Состояния: CANDIDATE → VERIFYING → READY, либо QUARANTINE / REJECTED; после фактического перехода в работу — CONVERTED.

## 4. Жёсткие ворота READY

Лид не может попасть в READY, если отсутствует хотя бы один критерий:
- идентифицирована организация или ИП;
- корректный ИНН;
- ИНН автоматически сопоставлен с авторитетным источником;
- организация соответствует целевой географии;
- организация соответствует целевой категории;
- имеется минимум один рабочий публичный телефон;
- подтверждена связь телефона с этой организацией или её официальным каналом;
- отсутствует дубль по ИНН;
- нет конфликта идентичности по нормализованному телефону, домену или названию;
- присутствует источник происхождения данных;
- известна дата последней проверки и она не вышла за допустимый срок.

Нет телефона или не подтверждён ИНН — нет READY.

## 5. ИНН

Проверка ИНН должна выполняться автоматически, без ручной очереди. ФНС через сервис «Прозрачный бизнес» предоставляет поиск по ИНН/ОГРН/наименованию, региону и видам деятельности и работает с открытыми данными ФНС. citeturn834427search0turn834427search2

В результат проверки записываются: найдено/не найдено, совпадение ИНН, наименование, статус, регион, дата контроля, источник и результат.

## 6. Телефон

Телефон — обязательное поле готового лида. Система нормализует номер и проверяет источник его принадлежности компании. Номер, найденный случайно без связи с организацией, не считается подтверждённым.

Один основной телефон показывается оператору; дополнительные остаются внутри карточки.

## 7. Категории

Категории задаются управляемым справочником, а не свободным текстом. Для каждой категории внутри системы хранятся ключевые признаки, релевантные ОКВЭД, исключения, география и типовые сигналы потребности.

Оператор не размечает найденные компании вручную.

## 8. Сигнал потребности

Текущая потребность — отдельный слой обогащения: вакансия, публичная заявка, запрос на услугу, иное подтверждаемое коммерческое событие или явное соответствие профиля компании целевой услуге.

Отсутствие мгновенного сигнала не должно автоматически выбрасывать качественную компанию, если она соответствует целевому профилю. Но сигнал должен повышать внутренний приоритет.

## 9. Дедупликация

Основной идентификатор организации — ИНН. Дополнительные ключи: нормализованный телефон, домен, нормализованное название + география.

Повторное обнаружение не создаёт второй рабочий лид: обновляются доказательства и дата проверки.

## 10. Внутренние пулы

Минимально достаточно четырёх логических пулов:
- Candidate;
- Verification;
- Ready;
- Quarantine/Rejected.

Они могут быть реализованы как внутренние статусы и представления одной таблицы. Пользователь их не обслуживает.

## 11. Объём выдачи

Система не должна работать по искусственному принципу «10/20/30 лидов в день».

Нужен целевой запас готовых лидов: если READY ниже заданного target stock, конвейер автоматически пополняет запас. Это запас рабочей базы, а не суточный лимит.

Для первого эксплуатационного теста разумно проверять конвейер на запасе порядка 200 готовых лидов, распределённых по заданным категориям, а не на маленькой фиксированной партии.

## 12. Приоритизация

Внутренний порядок выдачи строится по проверяемым факторам: соответствие категории, качество контактов, свежесть проверки, наличие сигнала потребности, география и отсутствие технических негативных признаков.

Ранжирование не превращается в ручную процедуру подтверждения.

## 13. Источники и интеграции

Логика должна быть независима от конкретного поставщика данных. Единый контракт источника: source → normalized candidate → verification → canonical lead.

Airtable умеет запускать скрипты по расписанию, вызывать внешние API через fetch() и принимать входящие webhooks. Это позволяет строить автоматический конвейер вокруг Airtable, но скриптовые действия имеют ограничения по времени и числу внешних запросов, поэтому цепочка должна быть короткой, идемпотентной и повторяемой, а не одним монолитным скриптом. citeturn205012search0turn205012search1turn205012search2

## 14. Отказоустойчивость

Ошибка отдельного источника не должна удалять READY, публиковать непроверенные данные или запускать бесконечный цикл повторной обработки.

Проблемная запись уходит в карантин с технической причиной и может безопасно пройти повторную обработку.

## 15. Что остаётся оператору

Только бизнес-действия: открыть лид, связаться, зафиксировать результат, отметить реальную потребность, перевести в работу и создать дальнейшее действие или заказ.

Оператор не подтверждает ИНН, не валидирует телефон, не запускает дедупликацию и не переносит записи вручную в READY.

## 16. Приёмочные критерии

Система считается соответствующей контракту только если контрольный прогон подтверждает:
1. кандидаты автоматически проходят конвейер;
2. все READY имеют обязательные поля;
3. у READY нет непроверенного ИНН;
4. у READY есть телефон;
5. дубли не попадают в рабочую выдачу;
6. нецелевые категории не попадают в READY;
7. оператору не требуется техническое подтверждение промежуточных этапов;
8. повторный запуск не создаёт дубликаты;
9. ошибки источников изолированы;
10. контрольная выборка READY подтверждает фактическое качество данных;
11. после каждого изменения выполняются интеграционные и регрессионные проверки всей цепочки.

## 17. Главный принцип

Airtable не должен быть интерфейсом для управления верификацией. Он должен быть интерфейсом для работы с уже подготовленным результатом.

Внутри: Discovery → Enrichment → Verification → Deduplication → Qualification → Ready Queue.

Снаружи: Готовые лиды → действие оператора.

## 18. Live-base reconciliation before implementation

Фактическая live-база сейчас не совпадает с чистым baseline 0.1.0 и текущим контрактом: в ней присутствуют дополнительные входящие/источниковые контуры, а операторский интерфейс показывает технические страницы. Это считается schema/interface drift.

До реализации Lead Factory в Airtable необходимо сначала составить точную карту соответствия GitHub contract ↔ live schema и устранить только те расхождения, которые мешают контракту. Нельзя молча продолжать поверх смешанной модели.

Критические правила реконструкции:
- «Лид» не должен маскироваться под «Клиента»;
- текущий объект «Клиент» сохраняет семантику фактического клиента;
- «Входящие» используется как внутренний intake-механизм только после подтверждения его соответствия контракту;
- источники, проверки и технические очереди не должны быть доступны на основной операторской поверхности;
- перед любым destructive schema change обязательны preflight, backup/export, postflight reconciliation и recovery evidence.

После синхронизации только с approved contract выполняется реализация в Airtable, затем полный end-to-end прогон поиска → проверки → READY → операторской обработки.
